## 3. Research Methodology

### 3.1 Research Design

This research employs a quantitative experimental methodology using black-box performance evaluation techniques. Four distinct research hypotheses are formulated as follows:

* **H1:** The predictive caching mechanism incurs negligible authorization latency overhead, maintaining performance and distributional parity without statistically significant differences under moderate load (500 RPS, $p_{\text{MWU}} > 0.05$) and demonstrating practical equivalence and non-inferiority via TOST within a 5% tolerance margin under high load (2000 RPS, $p_{\text{TOST}} = 0.0251 < 0.05$) relative to the unauthenticated baseline (PBS) and naive ZTA configurations.
* **H2:** Control-plane token revocation and invalidation broadcast latency satisfies the $100\text{ ms}$ operational design benchmark set by the author ($H_0: \theta_{\text{median}} \ge 100\text{ ms}$ vs. $H_1: \theta_{\text{median}} < 100\text{ ms}$), while bounding end-to-end data-plane cache synchronization within a deterministic polling interval ($\le T_{\text{tick}}$).
* **H3:** The graph-aware adaptive caching pipeline dynamically reduces the theoretical authorization exposure window (evaluated via closed-form analytical model) according to service risk sensitivity while maintaining practical p99 latency parity (no statistically significant difference, $|\delta| < 0.147$, with a Hodges-Lehmann location shift point estimate < 0.70% well within the $\pm 5\%$ reference margin and median difference < 3.6%) relative to the static TTL baseline.
* **H4:** Variations in topological communication patterns (linear, fan-out, and mesh) produce statistically significant differences in p99 latency due to request batching concurrency.

NIST SP 800-207 does not prescribe a numerical latency threshold for revocation. The standard qualitatively mandates that trust must be continuously re-evaluated and that policy administrators must retain the ability to terminate active connections upon security events (Rose et al., 2020). NIST SP 800-207A likewise specifies short-lived service identity credentials that undergo periodic re-authentication (ID-SEG-REC-2; Chandramouli & Butcher, 2023), without enforcing an explicit latency threshold. Consequently, this study establishes an operational design target of 100 ms for revocation latency ($H_0: \theta_{\text{median}} \ge 100\text{ ms}$ vs. $H_1: \theta_{\text{median}} < 100\text{ ms}$). This value was selected as an operational bound that remains substantially smaller than the 30-second default TTL in static configurations. This target represents a design benchmark defined by the author rather than a normative NIST mandate.

Hypotheses H1 and H3 are evaluated using the non-parametric two-sided Mann-Whitney U test ($\alpha = 0.05$). If the conventional significance test fails to reject the null hypothesis ($p > 0.05$), the evaluation protocol proceeds with the Two One-Sided Tests (TOST) equivalence procedure to positively verify whether performance differences reside strictly within an acceptable practical equivalence margin. Hypothesis H2 is evaluated both descriptively and inferentially via a one-sided Wilcoxon signed-rank test against the 100 ms design target set by the author ($H_0: \theta_{\text{median}} \ge 100\text{ ms}$ vs. $H_1: \theta_{\text{median}} < 100\text{ ms}$), whereas H4 is assessed using the multi-group Kruskal-Wallis H test, followed by post-hoc pairwise Mann-Whitney tests with Bonferroni correction.

Experiments were conducted on a Kubernetes testbed configured to emulate a cloud-native microservice architecture. By design, Kubernetes incorporates foundational principles consistent with Zero Trust concepts, enabling the deployment of internal cluster security controls backed by Network Segmentation, Role-Based Access Control (RBAC), and Open Policy Agent (OPA) (Verma, 2025). The independent variables comprise the authorization configuration (PBS baseline, naive ZTA, and ZTA with predictive cache), request workload (500, 2000, and 5000 RPS), and graph topology (linear, fan-out, and mesh). The measured dependent variables include 99th percentile end-to-end latency (p99), actual throughput, sidecar CPU and memory overhead, and certificate revocation latency. Each scenario was executed with 30 independent repetitions. It is noteworthy that each individual repetition (a 5-minute steady-state execution) generates between 150,000 and 600,000 individual HTTP requests depending on the target RPS, ensuring that internal p99 point estimates per run achieve empirical asymptotic stability. Consequently, the 30 repetitions represent 30 independent observations of the p99 metric itself, which are subsequently analyzed via non-parametric inferential statistics across groups. This sample size fulfills the required minimum for inter-repetition distribution estimation (Walpole et al., 2020).

### 3.2 System Architecture

The proposed system comprises three primary components integrated into the Istio service mesh data plane, as illustrated in Figure 1.

**Figure 1.** Predictive authorization caching system architecture

![Predictive authorization caching system architecture](figures/fig1-system-architecture.png)

The **Graph Topology Analyzer** monitors inter-service call patterns in real time by logging unique source-target identity pairs and computing invocation frequencies per minute. This component implements the betweenness centrality algorithm from the `gonum/graph` library to identify services occupying central structural roles within the dependency graph. Inactive graph edges exhibiting zero traffic for more than 120 seconds are automatically pruned to preserve graph fidelity.

The **Cache Distributor** receives the curated list of cache candidates from the Graph Topology Analyzer and generates delegation tokens cryptographically signed using HMAC-SHA256. Tokens are maintained in an active registry within the Cache Distributor (which exposes both a `PushToken` gRPC streaming service and HTTP REST endpoints `/tokens` and `/nonces/active`) and synchronized to Envoy sidecars via asynchronous periodic HTTP callouts (`DispatchHttpCall`, with an upper-bound deterministic self-healing reconciliation interval of $T_{\text{tick}} = 2\text{ seconds}$ in the WASM filter) alongside rapid control-plane gRPC push revocation broadcasting that immediately updates distributor revocation tables for rapid sidecar reconciliation upon active verification. Each token payload encapsulates the source SPIFFE ID, target SPIFFE ID, permitted actions, calibrated TTL, and a unique revocation nonce.

The **WASM Filter** operates within the Envoy sidecar proxy as an in-process local decision engine. The selection of WebAssembly is driven by its capability to provide secure, memory-isolated sandboxing and near-native runtime performance via the embedder runtime API (Zhang et al., 2025), thereby enabling local authorization evaluation without incurring inter-process communication overhead. In the Envoy concurrency model, each worker thread hosts an isolated, single-threaded WebAssembly VM instance executing an independent event loop; hence, in-memory cache lookups are entirely free from cross-thread locking contention. To maximize data-plane efficiency, the filter separates cryptographic overhead from the request critical path: (1) Cryptographic HMAC-SHA256 signature verification is performed asynchronously once upon token ingestion during distributor synchronization (`onTokenResponse`), and the active nonce table is atomically refreshed (`SyncActiveNonces`); (2) The inbound request critical path executes an ultra-lightweight, zero-deserialization and near-zero-allocation sequential validation pipeline in memory (eliminating per-request JSON parsing and reflection): (i) expiration check, (ii) active nonce membership verification against the atomic in-memory hash set ($O(1)$ lookup), and (iii) HTTP action matching against permitted methods. Requests lacking valid client identity are rejected fail-closed (HTTP 401 Unauthorized). Upon an in-memory cache hit (`Allow`), the WASM filter injects an internal verification header (`x-zta-cache-verified: true`) after stripping any external header of the same name, instructing the downstream Envoy `ext_authz` filter to bypass centralized OPA evaluation; conversely, on a `Miss` or `Expired` state, the request proceeds without this marker and is intercepted fail-closed by the centralized PDP. While HMAC-SHA256 is utilized in our implementation to minimize cryptographic verification latency within the WebAssembly sandbox during periodic ingestion (further optimized via delta-signature checks that skip re-verification for unchanged tokens), deployments operating under stricter untrusted-node threat models (where an adversary gaining root access to a compromised pod might inspect sidecar memory) can seamlessly substitute asymmetric Ed25519 signatures in `VerifySignature`, ensuring that Envoy sidecars possess only public verification keys while the `cache-distributor` retains the private signing key.

**Threat Model and Trust Boundaries.** The operational security model relies on explicit cryptographic and process isolation boundaries: (1) **Trust Domain**: Envoy sidecars run strictly inside the isolated Linux network namespace of each Kubernetes workload pod, communicating with upstream services over STRICT mutual TLS (mTLS) with SPIFFE identity verification; (2) **Header Sanitization**: To eliminate privilege escalation or forged header attacks, the WASM filter deterministically strips any inbound `x-zta-cache-verified` header from arriving HTTP requests before evaluating authorization. Only an in-memory cache hit inside the authenticated sidecar sandbox can inject the internal `x-zta-cache-verified: true` flag to signal the downstream `ext_authz` filter; (3) **HMAC Secret Custody**: Shared symmetric HMAC keys are distributed securely via Kubernetes Secrets mounted into memory-backed tmpfs volumes. While our default prototype employs HMAC-SHA256 for maximal WebAssembly throughput (with delta-signature caching), environments assuming untrusted or multi-tenant host nodes can substitute asymmetric Ed25519 signatures, restricting sidecars to public keys and keeping signing authority exclusive to the Cache Distributor.

A critical architectural distinction is drawn between **Control-Plane Revocation & Broadcast Latency**, representing the duration required by the revocation manager and distributor to revoke a nonce and broadcast the invalidation, and the **WASM Data-Plane Synchronization Bound** ($\le T_{\text{tick}} = 2000\text{ ms}$), which governs periodic state reconciliation within the sidecar sandbox.

### 3.3 TTL Computation Algorithm

The TTL for any directed service pair is computed using the following formulation:

$$\begin{aligned}
&\text{TTL}_{\text{raw}}(A \rightarrow B) = T_{\text{base}} \times w_f(e) \times (1 - p_s(e)) \times v_c(e) \\
&\text{TTL}(A \rightarrow B) = \min\left(t_{\text{remaining}},\ \min\left(T_{\max},\ \max\left(T_{\min},\ \text{TTL}_{\text{raw}}(A \rightarrow B)\right)\right)\right)
\end{aligned} \quad \text{...(1)}$$

where for each evaluated directed communication edge $e = (A \rightarrow B)$ across the service mesh:

- $T_{\text{base}} = 30,000\text{ ms}$ represents the base TTL duration, with uniform operational clamp bounds $T_{\min} = 5,000\text{ ms}$ and $T_{\max} = 30,000\text{ ms}$.
- $w_f(e) = \min\left(\dfrac{f_{\text{calls}}(e)}{100},\ 1.0\right)$ denotes the frequency weight, which scales TTL upward for frequently communicating service pairs, where $f_{\text{calls}}(e)$ is the call frequency per minute across edge $e$.
- $p_s(e) \in \{0.0,\ 0.3,\ 0.7\}$ corresponds to the target service data sensitivity penalty on edge $e$ for *low*, *medium*, and *high* sensitivity tiers, respectively, shortening cache retention for sensitive data assets. These penalty values reflect the three-tier data classification standard widely adopted in enterprise information security (ISO 27001), where high-sensitivity data mandates substantially restricted TTLs to minimize security exposure windows. Technically, data sensitivity ratings are defined declaratively in the OPA policy database (`data.service_rules` in `data.json`). The Graph Topology Analyzer and Cache Distributor query these sensitivity attributes via REST API calls to OPA per source-target SPIFFE pair, deterministically mapping them to the numeric penalty $p_s$ within the TTL computation module (`ttl.go`).
- $v_c(e) = \dfrac{t_{\text{remaining}}}{t_{\text{total}}}$ expresses the residual validity ratio of the workload mTLS certificate across communication pair $e = (A \rightarrow B)$, ensuring that the delegation token lifetime never outlasts certificate validity.

Because all scaling multipliers are bounded within $[0, 1]$, the maximum theoretical value produced by raw calculation is $T_{\text{base}} = 30,000\text{ ms}$. Operational clamping $[T_{\min}, T_{\max}]$ with $T_{\min} = 5,000\text{ ms}$ embodies an intentional architectural design trade-off (Clamping Option B): retaining cached decisions for a minimum lower bound $T_{\min} = 5\text{ seconds}$ amortizes sidecar network round-trip overhead and avoids cache thrashing against centralized PDPs during low call frequencies as well as high concurrency spikes, whereas under saturated call frequencies ($w_f = 1.0$), high-risk entities ($p_s = 0.7$) remain strictly bounded to a maximum exposure window of 9 seconds (compared to 30 seconds under static TTL). Furthermore, the hard ceiling $\min(t_{\text{remaining}}, \dots)$ strictly guarantees that the delegation token lifetime never outlasts the residual validity of the mTLS certificate even in scenarios where $t_{\text{remaining}} < T_{\min}$. On the prototype testbed, workload certificates were maintained at steady-state ($v_c = 1.0$) under standard 24-hour Istio rotation via `DefaultCertProvider`; boundary decay behavior ($v_c \to 0$) was independently verified via unit test suites (`ttl_test.go`).

For every directed communication pair represented as a directed edge $e = (A \rightarrow B) \in E$ originating from source node $\text{source}_e = A$, cache candidate prioritization is governed by the composite priority score formulated in Equation (2):

$$S(e) = w \times \hat{f}(e) + (1 - w) \times C_B(\text{source}_e) \quad \text{...(2)}$$

where $S(e)$ is the priority score for directed edge $e$, $\hat{f}(e)$ is the normalized call frequency scaled to $[0, 1]$, $C_B(\text{source}_e)$ is the normalized betweenness centrality of the source node, and $w$ is a tuning weight parameter ($w = 0.7$). Both components in Equation (2) are normalized to $[0, 1]$ using empirical maximum scaling across the observed graph topology:

$$\hat{f}(e) = \frac{f(e)}{\max_{e' \in E} f(e')}, \quad C_B(v) = \frac{C_B^{\text{raw}}(v)}{\max_{u \in V} C_B^{\text{raw}}(u)}, \quad C_B^{\text{raw}}(v) = \sum_{s \neq v \neq t \in V} \frac{\sigma_{st}(v)}{\sigma_{st}}$$

where $f(e) \equiv f_{\text{calls}}(e)$ represents the observed call frequency per minute across directed edge $e$, and $C_B^{\text{raw}}(v)$ is the raw betweenness centrality computed via Brandes' algorithm over the active adjacency graph as the ratio of shortest paths from vertex $s$ to $t$ passing through intermediate vertex $v$ ($\sigma_{st}(v)$) to the total number of shortest paths between $s$ and $t$ ($\sigma_{st}$) (Freeman, 1977). This empirical max-normalization ensures that both frequency and structural centrality metrics reside on commensurate scales regardless of graph diameter, subject to the conditions $\hat{f}(e) = 0$ whenever $\max_{e' \in E} f(e') = 0$ and $C_B(v) = 0$ whenever $\max_{u \in V} C_B^{\text{raw}}(u) = 0$ (e.g., across topologies lacking multi-hop transit paths).

This formulation assigns greater weight to call frequency (70%) relative to topological positioning (30%). This initial weighting ratio ($w = 0.7$) is established based on two considerations. First, caching benefits scale directly with entry reuse frequency: infrequently invoked service pairs derive negligible latency advantages from cache retention, making call frequency the primary predictor of cache utility. Second, centrality acts as a structural correction factor, ensuring that services acting as routing hubs across multiple execution paths receive prioritized cache allocation, as cache misses on hub nodes inflict disproportionate downstream delays. In a single-ingress topology where the source node occupies a peripheral position ($C_B = 0$), the composite priority formulation degenerates to a pure frequency function ($S(e) = w \cdot \hat{f}(e)$) with rank order invariance across $w$ (Kendall's $\tau = 1.0$). However, the structural advantage of betweenness centrality ($C_B > 0$) is empirically demonstrated in multi-hop topologies featuring intermediary bridge nodes under cache contention, as specifically evaluated in the ablation study in Section 4.9.

Every scenario was driven by the `constant-arrival-rate` executor in k6 for a 5-minute steady-state duration. The standardized execution procedure comprises five phases: (1) testbed state reset, (2) a 30-second warmup period with 10 Virtual Users (VUs), (3) a 30-second pre-test cooldown, (4) benchmark execution, and (5) a 120-second cooldown period between scenarios. For the fan-out scenarios (S07, S10), the target 2000 RPS workload is generated via three-endpoint parallel batch requests (`http.batch()` to `/api/products`, `/api/cart`, and `/health`), where the load generator arrival rate is calibrated up to $644.52\text{ batch iterations/s}$ corresponding to $\approx 1860\text{--}1934$ concurrent HTTP sub-requests/s. During the full 5-minute steady-state benchmark evaluation (30 repetitions in Table 4 and Section 4.5), CPU queue saturation on the 2-vCPU cluster stabilized the average effective throughput at $372.7\text{ batch iterations/s}$ ($1118.1\text{ HTTP sub-requests/s}$) for S07, $379.0\text{ batch iterations/s}$ ($1137.0\text{ HTTP sub-requests/s}$) for S10, and $383.0\text{ RPS}$ for S08.

Topology variations in this experiment are defined by the call patterns dispatched by the load generator (k6) to the frontend service, yielding distinct authorization evaluation dynamics across the Envoy sidecar. The linear topology queries a single endpoint per iteration (`/api/products`), prompting the sidecar to evaluate a single authorization pair. The fan-out topology dispatches three concurrent requests via `http.batch()` to `/api/products`, `/api/cart`, and `/health`, requiring the sidecar to evaluate three authorization pairs within a single iteration. The mesh topology dispatches one request per iteration in a round-robin rotation across all three endpoints, simulating a distributed communication spread. It should be noted that across these ten baseline testing scenarios (S01–S10), all endpoints (`/api/products`, `/api/cart`, and `/health`) are handled locally by the frontend service (whereas inter-backend service invocation chains are evaluated separately in the ablation study in Section 4.9). Topology variations across S01–S10 do not reflect deep inter-backend service invocation chains (chains); rather, they reflect distinct request patterns traversing the Envoy sidecar, producing varied authorization evaluation loads and graph topology recordings. Under the fan-out topology, p99 latency is governed by the slowest response within each batch (ceiling effect), whereas under the mesh topology, each request per iteration is evaluated independently. All communication is secured via mTLS and mediated by the WASM filter executing authorization decisions.

Crucially, this evaluation setup represents a controlled micro-benchmarking design to isolate the pure computational overhead of the WebAssembly decision engine from confounding backend execution jitter. In a star-like single-hop ingress topology where traffic originates from external clients, the ingress node exhibits zero betweenness centrality ($C_B(\text{frontend}) = 0$); hence, the priority score $S(e)$ is predominantly governed by normalized call frequency $\hat{f}(e)$. In complex production service meshes exhibiting multi-hop Directed Acyclic Graph (DAG) dependencies (such as the full 11-service Online Boutique dependency graph or large-scale enterprise microservice meshes where cache table capacity is restricted, $K_{\text{local}} < |E|$), intermediate routing hubs possess non-zero centrality ($C_B(v) > 0$), allowing structural positioning to actively prioritize critical transit paths. Across an $H$-hop invocation chain, cumulative latency savings scale additively as $\sum_{h=1}^H (\text{Latency}_{\text{PDP}, h} - \text{Latency}_{\text{WASM}, h})$.

Furthermore, to quantitatively substantiate the dynamic security exposure reduction claimed under Hypothesis H3, we define the **Maximum Authorization Exposure Window** ($W_{\text{exposure}}(p_s)$) incorporating the full closed-form clamping:

$$W_{\text{exposure}}(p_s) = \min\left(t_{\text{remaining}},\ \min\left(T_{\max},\ \max\left(T_{\min},\ T_{\text{base}} \times w_f \times (1 - p_s) \times v_c\right)\right)\right)$$

Under high-throughput steady-state operating conditions where call frequency saturates ($f_{\text{calls}} \ge 100 \implies w_f = 1.0$) and certificate validity remains at full cycle ($v_c \approx 1.0$, $t_{\text{remaining}} \ge T_{\max}$), noting that for all sensitivity classes $p_s \in \{0.0,\ 0.3,\ 0.7\}$, the product $T_{\text{base}} \times (1 - p_s) \in \{30\text{ s},\ 21\text{ s},\ 9\text{ s}\}$ consistently remains above the lower clamping threshold $T_{\min} = 5\text{ s}$, this expression reduces to $W_{\text{exposure}}(p_s) = T_{\text{base}} \times (1 - p_s)$. Under the Static TTL baseline configuration (S10), all cached authorizations persist unconditionally for $T_{\text{base}} = 30\text{ s}$ ($W_{\text{exposure}} = 30.0\text{ s}$). Conversely, under the Graph-Aware Adaptive TTL pipeline (S07), endpoints with medium sensitivity ($p_s = 0.3$, e.g., `/api/cart`) are dynamically constrained to $W_{\text{exposure}} \le 21.0\text{ s}$, yielding an **analytical model estimate of 30.0% reduction** in maximum authorization exposure window, while high-sensitivity communication channels ($p_s = 0.7$, e.g., payment and checkout operations) achieve a **70.0% reduction** ($W_{\text{exposure}} \le 9.0\text{ s}$). It is critical to state that this exposure reduction is an analytical estimate derived from the formal clamping equation under steady-state assumptions, rather than an empirical sidecar cache-hit logging observation, because cache-hit status was evaluated via end-to-end latency proxies rather than direct HTTP response headers. Crucially, this heightened security posture is attained without meaningful data-plane latency penalties, as evidenced by the lack of statistically significant p99 response time difference between S07 and S10 ($p_{\text{MWU}} = 0.842,\ \delta = -0.03$) alongside a Hodges-Lehmann location shift point estimate of $\hat{\theta}_{HL} = -40.67\text{ ms}$ ($|\hat{\theta}_{HL}| = 0.69\%$ of reference baseline median) well within the $\pm 5\%$ reference margin ($\Delta = 296.40\text{ ms}$, as detailed in Section 4.4 and Table 9).

### 3.6 Statistical Analysis Methods

Quantitative statistical evaluation follows standard non-parametric inferential procedures tailored for distributed systems performance analysis exhibiting characteristic heavy-tailed latency distributions. The Shapiro-Wilk test (Shapiro & Wilk, 1965) was evaluated at a significance level of $\alpha = 0.05$ to verify the non-normality of empirical latency distributions ($n = 30$ per scenario). Two-sample independent comparative hypotheses across baseline load scenarios were evaluated using two-sided Mann-Whitney U tests (Mann & Whitney, 1947), whereas directional evaluations in the ablation study (Section 4.9) employed one-sided Mann-Whitney U tests aligned with the a priori directional hypothesis of latency reduction, paired with Cliff's Delta ($\delta$) non-parametric effect size estimation (Cliff, 1993) under the empirical interpretation benchmarks established by Romano et al. (2006): $|\delta| < 0.147$ (*negligible*), $0.147 \le |\delta| < 0.330$ (*small*), $0.330 \le |\delta| < 0.474$ (*medium*), and $|\delta| \ge 0.474$ (*large*).

For multi-group independent comparisons across topology variations and resource overhead, the Kruskal-Wallis H test (Kruskal & Wallis, 1952) was employed, coupled with post-hoc pairwise Mann-Whitney U tests adjusted via Bonferroni correction ($\alpha' = \alpha / k'$ with $k' = 3$, yielding $\alpha' = 0.0167$) to strictly control family-wise error rate. Practical equivalence and non-inferiority were formally evaluated using the Two One-Sided Tests (TOST) procedure (Schuirmann, 1987; Lakens, 2017) via Hodges-Lehmann location shift estimation against a stringent equivalence margin of $\Delta = 5\%$ of the baseline median ($14.79\text{ ms}$ at 500 RPS, $111.37\text{ ms}$ at 2000 RPS linear, and $296.40\text{ ms}$ for the 2000 RPS fan-out baseline). Median difference 95% confidence intervals were estimated using non-parametric percentile bootstrapping with $B = 10,000$ resamples and a fixed pseudorandom seed (seed = 42) (Efron & Tibshirani, 1993).

Primary data for latency and throughput metrics were acquired from k6 JSON summary exports. Sidecar resource overhead metrics (CPU and memory) were exported from Prometheus via unweighted averages across all active `istio-proxy` sidecars in the `zta-research` namespace:
- Sidecar CPU utilization was computed via `avg(rate(container_cpu_usage_seconds_total{container="istio-proxy", namespace="zta-research"}[30s])) * 100` (%)
- Sidecar working-set memory was computed via `avg(container_memory_working_set_bytes{container="istio-proxy", namespace="zta-research"}) / 1024 / 1024` (MB).

This namespace aggregation calculates the mean across all injected pods running within `zta-research`. In scenarios S01–S09, deployment composition was strictly identical with six active pods (`frontend`, `productcatalogservice`, `cartservice`, `opa`, `graph-analyzer`, and `cache-distributor`), ensuring consistent denominators across all primary comparisons (even though `productcatalogservice` and `cartservice` were idle in linear benchmarks S01–S06, their sidecars remained running and contributed to the namespace average denominator). In S10, `graph-analyzer` was scaled down to simulate an absent analyzer, reducing active sidecars from six to five; hence, slight shifts in namespace-wide resource averages reflect pod denominator changes rather than internal WASM filter efficiency changes.

### 3.7 Data Processing and Verification Pipeline

Data processing was executed via an automated three-stage analytical pipeline. In the first stage, the script `analyze-all-data.py` (Python 3.10, pandas 2.2, scipy 1.14, numpy 2.2) consolidated 300 k6 JSON summary files and 300 Prometheus CSV files into a unified dataset. This script extracted primary metrics (p99 latency, mean latency, actual RPS, and error rate) across all experimental runs, generating four primary dataset files: `latency-all-scenarios.csv`, `resource-overhead.csv`, `cache-performance.csv`, and `revocation-latency.csv`.

In the second stage, the validation script `validate-data.py` conducted an automated audit across 10 distinct integrity checks: (1) completeness of all 600 data files (300 JSON + 300 CSV), (2) verification of 30 repetitions per scenario, (3) JSON parsing integrity and required metric presence, (4) verification that error rates remained below 1%, (5) assessment of actual throughput deviation against targets, (6) confirmation of test durations approximating 300 seconds, (7) outlier detection using the $1.5 \times \text{IQR}$ rule, (8) Prometheus CSV schema validation, (9) cross-validation of data provenance (original vs. rerun sources), and (10) descriptive statistical sanity checks.

In the third stage, all statistical tests (Shapiro-Wilk, Mann-Whitney U, Cliff's Delta, and Kruskal-Wallis) were computed automatically by the analysis scripts and exported as structured CSV files in `data/reports/`. Canonical statistical visualizations were generated using `generate-figures.py` (matplotlib 3.10). All analytical scripts are publicly available within the replication repository to support independent reproducibility.
